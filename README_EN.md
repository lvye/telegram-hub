# Telegram Hub

[中文](./README.md)

An RSS / TwitterAPI.io-to-Telegram aggregator built for Cloudflare Workers. Cron only produces source jobs, D1 stores stable identities and runtime state, and Cloudflare Queues handles asynchronous ingestion, delivery, backoff, and dead-lettering.

## Runtime model

```text
Cron → claim due sources in D1 → Ingestion Queue sourceId + queueToken
     → source lease → fetch/parse RSS or poll TwitterAPI.io
     → D1 items + deliveries → Delivery Queue deliveryId
     → queue() consumer → D1 lease → Telegram → sent/retry/dead

Exhausted infrastructure retries → native DLQ consumer → D1 retry/dead

Daily UTC Cron → compact old terminal payloads while retaining identity
```

The Worker only exposes read-only `GET /health` and `GET /health/ready` endpoints. Readiness checks D1, stopped sources, and blocked/dead runtime states. There is no public HTTP endpoint that can trigger Telegram delivery.

## Highlights

- TypeScript ES Module Worker with bindings generated by `wrangler types`
- One Worker handles `scheduled()`, `queue()`, and read-only `fetch()` events
- A Source Runtime separates source instances, adapters, identity namespaces, and delivery destinations
- `source_runtime_state` stores provider-neutral cadence, leases, consecutive failures, and next-poll state; `source_ingestion_state` remains provider checkpoint state
- Cron emits one job per due source; the ingestion consumer uses queue tokens and source leases to reject duplicate or expired jobs
- Source 429/5xx failures combine `Retry-After`, exponential backoff, and jitter; permanent 4xx failures become `blocked`, exhausted ingestion DLQ jobs become `dead`, and both probe recovery after separate cooldowns
- RSS and TwitterAPI.io adapters emit provider-neutral `CanonicalItem` batches; one ingestion service owns deduplication, persistence, and checkpoint commits
- Telegram chat IDs, parse mode, and message format live in destination configuration rather than discovery sources
- `(source_key, external_id)` identity instead of a publication-date watermark
- TwitterAPI.io and legacy RSS share indexed `TWITTER` identity aliases; RSS keeps its provider GUID while tweet status IDs deduplicate across providers
- The latest known RSS tweet identity becomes the handoff high-water, avoiding wall-clock gaps; table-backed accounts fail independently instead of fetching the same RSS fallback repeatedly
- API cursors, pending high-water, and committed high-water are durable; a page-budget stop resumes on the next eligible Cron
- The full byte-bounded feed is scanned, while each run writes only the oldest 50 unseen identities; repeated feeds do not rewrite `items/deliveries`, and delayed items beyond the first window are drained later
- Per-destination delivery state and recoverable D1 leases
- Queue-delayed retries for retryable Telegram responses; permanent API errors go directly to `dead`
- Native Cloudflare DLQ reconciliation; non-exhausted application work returns to `retry`
- Batched D1 statements stay within the per-invocation query budget of Workers Free
- D1, Cron, Queue, and HTTP tests run inside workerd

## Provision and deploy

```bash
npm ci
npx wrangler d1 create rss
npx wrangler queues create telegram-delivery
npx wrangler queues create telegram-delivery-dlq
npx wrangler queues create source-ingestion
npx wrangler queues create source-ingestion-dlq
```

Copy the returned D1 `database_id` into `wrangler.toml`, then configure the required secrets:

```bash
npx wrangler secret put TELEGRAM_BOT_TOKEN
npx wrangler secret put IT_HOME_CHAT_ID
npx wrangler secret put TWITTER_CHAT_ID
npx wrangler secret put TWITTER_RSS_URL
```

### Optional TwitterAPI.io provider

Keep the API key in a Worker secret and maintain account subscriptions in the D1 `twitter_subscriptions` table:

```bash
npx wrangler secret put TWITTERAPI_IO_API_KEY
```

After applying migrations, add accounts through the Cloudflare Dashboard or a one-off `wrangler d1 execute --remote --command`. Never place real account INSERTs in migrations, seed SQL, or other Git-tracked files. Each row carries a stable `provider_state_key`, a handle without `@`, an `active/paused/archived` status, and per-account polling settings. Pausing a row preserves its cursor and high-water.

An empty table keeps the single RSS source active. Once subscription rows exist, active rows expand into API sources that share the existing `TWITTER` item identity and Telegram destination. The legacy `TWITTERAPI_IO_USER_ID` / `TWITTERAPI_IO_USER_NAME` single-account bindings remain compatible but are no longer recommended.

Optional tuning bindings default to a five-minute cadence, one page of at most 20 tweets per invocation, and replies disabled:

```bash
npx wrangler secret put TWITTERAPI_IO_POLL_MINUTES
npx wrangler secret put TWITTERAPI_IO_MAX_PAGES
npx wrangler secret put TWITTERAPI_IO_INCLUDE_REPLIES
```

Migration `0004` backfills tweet-status-ID aliases from historical Twitter URLs. Migration `0005` creates only the subscription schema and contains no account rows. Each subscription has independent durable provider state and bootstraps only from that account's historical URLs, so one account cannot inherit another account's high-water. Page-budget continuations resume from the stored per-account cursor.

The endpoint does not currently publish a stable media-field contract, so the API provider sends text plus the source link; the RSS fallback retains its existing image parsing. The provider explicitly warns that frequent polling is expensive, so review cost before increasing cadence or page depth. See the [endpoint documentation](https://docs.twitterapi.io/api-reference/endpoint/get_user_last_tweets).

Once TwitterAPI.io has successfully delivered a new tweet, do not roll back to an older Worker that only understands RSS provider GUIDs; use roll-forward from that point. An empty subscription table keeps RSS behavior; active rows without the API key fail with an explicit configuration error.

Apply migrations before deploying the Worker:

```bash
npm run db:migrate:remote
npm run check
npm run deploy
```

Migration `0003` is additive and backfills the legacy table. Legacy `pending` rows become `blocked` because their Telegram outcome is ambiguous. During the observation window, the new Worker uses a persistent `updatedAt` cursor to reconcile late legacy writes immediately before dispatch, mirrors successful deliveries to the old sent ledger, and keeps that ledger bounded during daily cleanup.

Migration `0004` adds provider handoff/pagination state and an indexed `item_identity_aliases` table, including a tweet-status-ID backfill from historical Twitter URLs.

Migration `0005` adds `twitter_subscriptions`; its rows are operational data and must remain outside Git.

Rollback is viable for the existing source set while the legacy assumption of globally unique GUIDs holds and before the API provider delivers new content. After the first API delivery, the old RSS-only Worker cannot relate an API tweet ID to its provider-specific RSS GUID, so use roll-forward. Do not add a source that can collide on GUID with another source until the bridge is removed; the old schema cannot represent source-scoped identity. For a near-zero-duplicate code cutover, pause the old Cron/Queue consumers and wait for in-flight invocations before applying migrations and deploying. Otherwise, accept a small overlap window. Remove the bridge and legacy table only in a later migration after the observation period.

## Adding a source

1. Implement `SourceAdapter` and return provider-neutral `CanonicalItem` values plus an optional checkpoint transition.
2. Register the adapter without adding provider branches to `IngestionService`.
3. Have `SourceCatalog` provide a stable `sourceId`, `identityNamespace`, `destinationKey`, and cadence. Keep credentials in runtime adapter configuration rather than durable jobs.
4. Register presentation behavior in the destination/formatter layer; do not put chat IDs or message formats back into source definitions.
5. Preserve the identity namespace and design an explicit cutover when switching providers.
6. Add adapter-contract and fixture tests for pagination, provider deduplication, initial cutover, delayed content, and Telegram formatting.

Feed parsers interpret provider formats, adapters build canonical items, and the delivery layer owns final Telegram formatting and revalidates rich text at the send boundary.

## Delivery semantics

Cloudflare Queues provides at-least-once delivery. D1 terminal-state checks and leases absorb most duplicates, but a process interruption after Telegram accepts a message and before D1 records `sent` can still cause a rare duplicate. This window cannot be fully removed without idempotency support from the external API.

`destinationKey` is the durable delivery identity. Keep the key stable when only changing the Telegram chat. A new key creates independent deliveries for known items in the current source window (bounded to 50 per RSS run), which enables controlled routing/backfill. Do not point two keys at the same chat unless duplicate presentation is intentional.

Queue `max_retries` and the DLQ cover infrastructure-level failures. Telegram 429, 408, and 5xx responses are rescheduled by the application state machine using `available_at`; permanent 4xx responses are marked dead instead of being pointlessly dead-lettered.
